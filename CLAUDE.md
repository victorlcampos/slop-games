# slop-games — house rules

A collection of games that run entirely in the browser. Each game is **a single
HTML file** that opens on a double click: no server, no install, no account, no
backend.

This document applies to every game in the repository — the ones already here
and the ones still to come.

---

## 1. What is not up for negotiation

These six rules define the project. If an idea runs into any of them, the idea
changes — not the rule.

1. **100% client-side.** No backend, no server-side build, no database. Whatever
   the game needs to keep goes in `localStorage`.
2. **One `index.html`.** The final artifact is a single file, with HTML, CSS, JS
   and assets embedded. No `<script src>`, `<link rel=stylesheet>`, `<img src>`
   or `fetch` pointing at a neighbouring file — over `file://` that breaks (or
   hits CORS).
3. **It has to open on a double click.** The acceptance test is literal: open
   `dist/<slug>/index.html` from the Finder, with no local server, and the game
   runs. If it needs `python -m http.server` to work, it is wrong.
4. **Zero CDN, zero external asset.** No `unpkg`, no `jsdelivr`, no Google
   Fonts, no downloaded sprite, no remote `.mp3`. Everything the game uses is
   inside the file. Libraries come in through the bundler, never through
   `<script src>`.
5. **Assets generated by code.** Sprites, textures, terrain, sound — all drawn or
   synthesised at runtime. That is what keeps the file small and the project free
   of a binaries folder. Not one game here ships **a single image**: Zoo Tycoon
   draws 219 species from 28 parameterised body plans, SkiFree 3D generates
   terrain and snow from noise, World Drive assembles its scenery from vector
   data, and Animals vs Monsters draws 33 creatures with a 200-line crooked-line
   engine. Even the language picker's flags are drawn on a canvas — the 🇧🇷 emoji
   has no glyph on Windows, and there the picker would become the letters "BR" in
   a box.
6. **Every game speaks English and Portuguese.** Two flags, one choice, and it
   covers the whole catalog. The mechanism lives in slopkit (section 2c) — it is
   not reimplemented per game.

### "Runs on the client" ≠ "runs offline"

A game may call a public API at runtime and still be 100% client-side — that is
World Drive, which fetches its streets from Overpass (OpenStreetMap). What it may
not have is **a backend of its own**. When a game depends on the network, mark
`"offline": false` in `game.json` and explain in `"note"` — the index shows a
"needs network" badge so the player isn't caught out.

## 2. Anatomy of a game

Every game lives in `games/<slug>/` and honours this contract:

```
games/<slug>/
  game.json        # metadata — this is what feeds the index
  package.json     # needs a "build" script (and a "test", if it has one)
  build.mjs        # produces dist/index.html
  src/             # the real code, in modules
  test/            # the game's own test, on slopkit/testing
  dist/index.html  # generated, not in git
  README.md        # how to play, controls, what is interesting about it
```

Only two things are mandatory, and the root build enforces both:

- **`game.json`** with `slug` matching the folder name, and `name`/`description`
  in both languages.
- **`npm run build` producing a self-contained `dist/index.html`** — the
  orchestrator checks for any leftover external reference and fails the build if
  it finds one.

Two more are strongly recommended, and the catalog test uses them when present:

- **`window.__game`** with at least `{ name, viewport, i18n }`, where `viewport`
  exposes `W` and `H` (the logical measurements). That is how the test turns a
  touch into a coordinate without guessing — see section 6 — and it is through
  `i18n` that it checks the flag really switches.

The **slug stays as it is**, even in Portuguese: it is the published URL
(`/animais-vs-monstros/`), and the game already carries both names through
`game.json`.

The rest (which bundler, how `src/` is organised) is each game's own choice.

### `game.json`

```json
{
  "slug": "my-game",
  "name": { "en": "My Game", "pt": "Meu Jogo" },
  "emoji": "🎮",
  "description": {
    "en": "One line that makes you want to click. No empty adjectives.",
    "pt": "Uma frase que dê vontade de clicar. Sem adjetivo vazio."
  },
  "tags": ["2d", "puzzle"],
  "libs": ["three.js"],
  "offline": true,
  "note": { "en": "Only when offline:false…", "pt": "Só quando offline:false…" },
  "year": 2026
}
```

`libs: []` becomes "no dependencies" on the card, which is a badge of honour
here.

**Tags are English slugs** (`tower-defense`, `open-world`) and the translation
lives in `TAGS`, in the root `build.mjs` — in one place. An unknown tag fails the
build instead of showing up raw on a card.

A `name` or `description` missing either side **fails the build**. On purpose:
half a translation is exactly the kind of thing that only surfaces when somebody
flips the flag.

## 2b. The slopkit

The four games solved the same handful of problems — viewport, loop, save, mute —
and each solved them its own way. `lib/` keeps the best answer of each, and a new
game starts from there instead of reinventing (worse).

```bash
npm i slopkit          # it is already a workspace: just declare the dependency
```

```js
import { createViewport, createLoop, createSave, createSound, createI18n } from 'slopkit';
```

### Where each piece came from

This is not an opinion: every piece was chosen by comparing the four
implementations that already existed.

| Piece | Came from | Why it won |
|---|---|---|
| `viewport` — elastic width | Animals vs Monsters | fixed logical height, width following the aspect ratio: fills any monitor with no bars and no distortion |
| `viewport` — DPR ceiling | Zoo Tycoon | an **adaptive** ceiling (1.6 on a small phone, 2 elsewhere); DPR 3 triples the fill area for no visible gain on a cartoon outline |
| `loop` — fixed step | Zoo Tycoon | it was the only one with an accumulator and a guard; the other three used raw dt, and with raw dt a game behaves differently at 60 and at 144 Hz |
| `save` — one format | Zoo Tycoon | the same snapshot serves the autosave and the file. Two formats become two saves drifting apart |
| `save` — normalise | Animals vs Monsters | every save read goes through a function that fills in what's missing; an old save loses a field, never the run |
| `save` — download a file | Zoo Tycoon | `revokeObjectURL` with slack (revoking early cancels the download in Safari) |
| `sound` — persisted mute | 3 of the 4 | Animals was the only one that forgot the choice on reload |
| `i18n` — dictionary by phrase | new | with one object per language, a key exists in one and vanishes in the other with nobody noticing |

### The rules that came out of it

1. **Fixed-step simulation, free drawing.** `update(h)` always receives the same
   `h`. If your `update` uses whatever dt arrives, the game changes behaviour
   with the player's monitor.
2. **Never trust what you read off disk.** Every save goes through `normalize`.
   The game has to open even with a save two versions old, hand-edited.
3. **The logical height is fixed; the width is not.** Draw against `H` and read
   `W`. Anything with an absolute X position only survives inside a *frame* — and
   a frame **scales** when the screen is narrower than it is, or it spills (a
   16:10 monitor gives 1152 of logical width, not 1280).
4. **A DPR ceiling.** Rendering a cartoon outline at 3x is spending three times
   as much for nobody to see a difference.

### Who uses what

The four games share the build and the test scaffold. Beyond that, each adopted
what brought a real gain — swapping good code for equivalent code is risk with no
return:

| | build | test | save | viewport | loop | sound | i18n |
|---|---|---|---|---|---|---|---|
| Animals vs Monsters | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| SkiFree 3D | ✅ | ✅ | ✅ | — | — | — | ✅ |
| World Drive | ✅ | ✅ | ✅ | — | — | — | ✅ |
| Zoo Tycoon | ✅ | ✅ | — | — | — | — | ✅ |

Zoo is the origin of half the kit — its save, its viewport and its loop **are**
the standard; it just doesn't import the module because it runs in global scope
(`window.Slop` is there if it needs it). SkiFree and World Drive have their
canvas managed by three's renderer, so `slopkit/viewport` doesn't apply to them.

About the loop, the criterion is **not 2D versus 3D** — it is whether the
acceleration depends on the velocity it is itself changing:

```js
// Animals vs Monsters — constant speed, dt enters linearly:
m.x -= speed * dt;             // two steps of dt/2 give the same as one of dt

// SkiFree and World Drive — drag as a function of the velocity itself:
a -= drag * v * v;             // the drag changes when v changes…
v += a * dt;                   // …so subdividing dt gives a different result
```

In the first form a fixed step is a free swap — that is why Animals, which is 2D
but could have been anything, migrated without rebalancing a thing. In the
second, the step size changes the terminal velocity and the acceleration curve:
the game responds differently and the saved records stop being comparable.
Migrating is possible, but it comes with playtesting and reworked constants —
design work, not style.

(Careful with the easy guess: the exponential `damp` SkiFree uses everywhere —
`lerp(a, b, 1 - exp(-λ·dt))` — **is** invariant to dt subdivision, on purpose.
The problem is only in the velocity integration.)

## 2c. The two flags

Every game here speaks English and Portuguese. **English is the product
default** — but a browser asking for Portuguese gets Portuguese; the fallback
only decides what a French or Japanese visitor sees. The choice lives under a key
the whole catalog shares (`slop:lang`), so picking a flag on the index carries
into the next game the player opens.

```js
import { createI18n, mountLangPicker, bindText } from 'slopkit';
const i18n = createI18n({ dict: { play: { en: 'Play', pt: 'Jogar' } } });
```

**The dictionary is keyed by phrase, not by language.** It is the decision that
matters most here:

```js
// right: the missing translation shows up on the line you are editing
{ play: { en: 'Play', pt: 'Jogar' } }

// wrong: `pt.play` can simply not exist, and you only find out when a
// player flips the flag and sees the raw key on screen
{ en: { play: 'Play' }, pt: { /* … */ } }
```

`missingKeys(dict)` turns that into a test. Use it.

### Where the translation goes

There is no single place, and there shouldn't be — the text lives next to what it
names:

| The phrase is… | Write it like this | Who uses it |
|---|---|---|
| static copy of an HTML menu | `data-pt` / `data-en` on the element itself | SkiFree, World Drive, the index |
| an attribute (title, placeholder) | `data-pt-title="…"` | World Drive, Zoo |
| a field in a dense data table | `'Savanna\|Savana'`, read by the game's `LN()` | Zoo (219 species) |
| a sentence assembled at runtime | dictionary + `t('key', { n })` | all of them |

`bindText(i18n)` handles the first two forms: it finds the marked elements and
swaps the text on every flag change. Because the text is in the HTML, it shows up
**before** any JavaScript runs — there is no flash of empty screen. The markup
carries the English side, which is the default; `bindText` swaps to Portuguese
only if the flag asks.

### The picker

```js
mountLangPicker(i18n);              // fills every [data-lang-picker] on the page
drawLangPicker(ctx, i18n, { x, y }) // a game that draws its menu on canvas
```

The canvas one returns the touch zones; `pickLangAt(zones, x, y)` says which flag
the finger landed on. Both versions paint the same flag: `drawFlag` draws into
any 2D context and `flagDataURL` runs the same routine on an offscreen canvas for
the DOM to use as an `<img>`.

**A canvas game gets i18n nearly for free** — the screen is repainted every
frame, and switching language is the next frame reading a different string. What
needs attention is the sprite cache: if the drawing has text baked in, the cache
key has to include the language. And if the sprite is seeded from a name, keep a
stable identity (Zoo has `sp.key`) — otherwise flipping the flag redraws all 219
animals.

## 3. Technologies

### Use

| For | Use | Why |
|---|---|---|
| 3D | **three.js** (`npm i three`) | It is what the 3D games here use. The bundler tree-shakes it. |
| 2D | **plain Canvas 2D** | No 2D library justifies its weight. Zoo Tycoon is 291 KB **with** 219 drawn species; Animals vs Monsters, 138 KB with 33. |
| Sound | **Web Audio API** by hand | Oscillators and synthesised noise. Never an audio file. |
| UI/HUD | **plain DOM + CSS** | Overlaid on the canvas. Faster to change than UI drawn inside the canvas. |
| Saved state | **`localStorage`** | The only storage available with no backend. |
| Build | **esbuild** | Fast, one dependency, `bundle + minify` covers everything. |

### Avoid

- **A UI framework** (React, Vue, Svelte) — the game is a canvas with a HUD; the
  framework is weight and indirection for no return.
- **A game engine** (Phaser, PixiJS, Babylon) — they solve problems these games
  don't have and fatten the file. Canvas 2D and three.js cope.
- **TypeScript** — no game here uses it; it adds a build step with no gain at
  this scale. If a new game wants it, let that be a conscious decision isolated
  to it.
- **Anything that needs a server** — your own WebSockets, backend multiplayer,
  save upload.

### File weight

Current reference: Animals vs Monsters 138 KB and Zoo Tycoon 291 KB (both with no
libraries), World Drive 596 KB and SkiFree 3D 702 KB (three.js minified in). The
last two carry all of three — that is the price of 3D.

Past ~2 MB, investigate before accepting it: it is almost always an asset
embedded as base64 or a bundle that wasn't minified.

## 4. Creating a new game

```bash
mkdir -p games/my-game/src
cd games/my-game
```

**1. `package.json`** — the name has to match the slug:

```json
{
  "name": "my-game",
  "version": "1.0.0",
  "description": "One line.",
  "type": "module",
  "private": true,
  "scripts": { "build": "node build.mjs" },
  "license": "MIT",
  "dependencies": { "three": "^0.185.1" }
}
```

**2. `build.mjs`** — three lines, because the build lives in the kit (section 5):

```js
import { build } from 'slopkit/build';

await build({ root: import.meta.dirname });
```

**3. `template.html`** — HTML, CSS and the bundle's placeholder:

```html
<!doctype html>
<html lang="en">
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width, initial-scale=1">
<title>My Game</title>
<style> /* all the CSS here — no separate file */ </style>
</head>
<body>
  <canvas id="canvas"></canvas>
  <div id="hud"><!-- HUD in DOM --></div>
<script>/*__APP__*/</script>
</body>
</html>
```

**4. `game.json`** with the metadata (section 2).

**5. Wire up slopkit** — viewport, loop, save, sound and language already solved
(2b and 2c):

```js
import { createViewport, createLoop, createSave, createI18n } from 'slopkit';

const i18n = createI18n({ dict: { play: { en: 'Play', pt: 'Jogar' } } });

const vp = createViewport(document.getElementById('canvas'));
vp.watch(() => reposition());

const vault = createSave({ game: 'my-game', version: 1, initial: freshSave, normalize, i18n });
let state = vault.load();

createLoop({
  step: 1 / 60,
  update: (h) => world.tick(h),       // h is always the same
  draw: () => { vp.begin(); paint(vp.ctx); },
}).start();

window.__game = { name: 'my-game', viewport: vp, i18n };   // test bridge (section 6)
```

**6. Register and check** — at the repository root:

```bash
npm install          # the games/* workspace picks the new game up on its own
npm run build        # builds everything and regenerates the index
npm test             # checks that it opens over file:// and clears the floor
```

The index **does not need editing**: it is generated from the `game.json` files.

## 5. Build

Everything from the root:

```bash
npm install            # once (npm workspaces handles the games and the lib)
npm run build          # builds every game + the index -> dist/
npm run build zoo-magnata   # builds one game (and the index)
npm run open           # builds and opens the index in a browser
```

The root `build.mjs` runs each game's `npm run build`, validates the result,
copies it to `dist/<slug>/index.html` and assembles the index from
`site/index.html` + the `game.json` files. `dist/` is generated and **not
committed**.

The index goes through `slopkit/build` too: it carries the `/*__APP__*/` mark and
a `site/index.js` that wires up the language picker. There was no reason for the
catalog to have a bundler of its own.

### Each game's build

Every game uses the same build, which lives in the kit. The game's `build.mjs` is
the configuration, not the implementation:

```js
import { build } from 'slopkit/build';

await build({ root: import.meta.dirname });
```

That bundles `src/main.js` with esbuild, injects it at the `/*__APP__*/` mark in
`template.html`, minifies and writes `dist/index.html`. That is the normal case.

**Aliases** — when a library is vendored instead of coming from npm (SkiFree has
three in `vendor/`):

```js
await build({
  root: import.meta.dirname,
  alias: { 'three/addons': 'vendor/addons', three: 'vendor/three.module.js' },
});
```

**`concat` mode** — for code that shares a global scope and depends on file
order, with no `import` at all (Zoo Tycoon). It still minifies everything
together, and `globals` hangs an ESM package off a global variable, which gives
those games access to slopkit without rewriting their whole scope:

```js
await build({
  root: import.meta.dirname,
  mode: 'concat',
  globals: { Slop: 'slopkit' },       // becomes window.Slop
  files: ['src/01_i18n.js', 'src/02_util.js', /* … in exact order */],
});
```

### Installable on a phone (PWA)

**The app is the catalog, not each game.** One icon on the home screen opens the
index, and from there you enter any game — four separate icons would just be
clutter.

The manifest lives in the root `build.mjs`, embedded in the index as a `data:`
URI along with an SVG icon. `scope: './'` makes the games run inside the app, and
`display: standalone` keeps the system status bar — a player wants to see the
clock and the battery.

**There is no service worker, and none is missed.** Everything here is already a
single HTML file with nothing to fetch. (Chrome's automatic install prompt
requires a SW; "Add to Home Screen" from the menu works without one, and on iOS
that is the only way anyway.)

`orientation` in `game.json` is optional, defaulting to `any`. Declare
`landscape` only if the game genuinely doesn't work upright.

The installed manifest speaks **one language only** — an app's name doesn't
change with the flag. It uses the English side; the `<title>`, which JavaScript
*can* update, is what follows the player's choice.

### The exit to the catalog (mandatory)

In app mode **there is no browser chrome**. Whoever enters a game is stuck: on
Android there is still the system back button, on iOS there is nothing. So every
game here has to offer the way back.

It goes **on the game's home screen** — the menu, the splash, the map — wearing
the game's own look, and not as a floating `←` over the match. An overlaid button
gets in the way of whoever is playing and belongs nowhere; on the home screen it
is just one more menu option, which is where a player looks for "exit".

The contract has two ends: **the game says where it wants the exit, the catalog
switches it on.**

**A game with a DOM menu** — declare the element hidden, wearing **the button
class the game already has**, not a new style:

```html
<!-- SkiFree: .btn.ghost, the secondary next to "Ride the mountain" -->
<a class="btn ghost back-to-games" data-back-to-catalog data-t="slop.backToCatalog" hidden></a>
<!-- World Drive: .chip, the same pill as the city shortcuts -->
<!-- Zoo Tycoon: .btn, the house's cartoon button             -->
```

The phrase comes from the kit (`slop.backToCatalog`), so it already arrives in
both languages — no need to rewrite it per game. The `.back-to-games` class
handles only what isn't visual (`inline-flex`, the emoji's `gap`, dropping the
underline, hiding). **Never leave the `<a>` without a `color`**: without one it
inherits the browser's link blue (`#0000EE`) — and if the border is
`currentColor`, that goes with it. It happened in three games at once here: over
SkiFree's and World Drive's dark backgrounds the button was unreadable.
Inheriting the game's class fixes that for free, and it is what makes the exit
look like part of the menu instead of a graft. The catalog test enforces the
colour.

**A game that draws on canvas** — read `window.__catalog` and draw it your way:

```js
...(window.__catalog ? [{ label: t('slop.backToCatalog'), action: 'catalog' }] : []),
// and on the click:
window.location.href = window.__catalog;
```

**A drawn button measures its text.** "restart" and "recomeçar" are not the same
length; a fixed width clips one of them. Animals measures with `measureText` and
adds the padding — that is what lets the bar survive a flag change.

In both cases the root build injects, **only into the published copy**, a script
that defines `window.__catalog` and reveals the marked elements. Whoever
downloads the game's HTML on its own doesn't get that script: the element stays
hidden and no link is left pointing at a catalog that isn't there.
`games/<slug>/dist/index.html` stays pure.

The catalog test enforces both ends — that the game offers the exit and that the
loose file does not show it.

### The contract

- **`template.html`** with the `/*__APP__*/` mark where the bundle goes.
- **`npm run build`** running `node build.mjs`.
- The result is validated: if a `<script src>` or a `<link stylesheet>` pointing
  outside survives, the build **fails** instead of producing an HTML that won't
  open over `file://`. That is rule nº 2 enforced by machine.

### The two traps, solved once

They were duplicated across two different builds before this became one thing:

1. **A `</script>` inside the bundle closes the tag mid-game.** Every piece of
   text that goes into the HTML has to escape it.
2. **`String.replace` interprets `$&` and `$1` in the replacement text** — and
   every minified bundle contains those characters. That is why the substitution
   is always done with a function, never with a string.

### What the standardisation bought

| Game | Before | After | |
|---|---|---|---|
| SkiFree 3D | 1622 KB | **702 KB** | the homegrown bundler didn't minify |
| Zoo Tycoon | 377 KB | **291 KB** | `cat` didn't minify |
| World Drive | 581 KB | 596 KB | already esbuild |
| Animals vs Monsters | 111 KB | 138 KB | already esbuild |

Today's numbers already include the second language: the duplicated text costs
between 10 and 25 KB per game, and the i18n kit (dictionary, drawn flags, picker)
comes in at ~4 KB. Cheap for what it delivers.

Gone along the way: a 150-line homegrown ES bundler (SkiFree), a bash `build.sh`
(Zoo) and three copies of the same template-injection logic.

## 6. Tests

```bash
npm test               # the kit's unit tests + the floor every game clears
npm run test:games     # each game's own test, if it has one
node lib/test/kit.test.mjs            # only the unit tests (milliseconds, no Chrome)
node games/<slug>/test/game.test.mjs  # only one game
```

### Three layers, and what goes in each

1. **Unit, no browser** (`lib/test/`) — the pure arithmetic: how many steps the
   loop takes, what width the viewport picks, what normalisation does to an old
   save. Runs in milliseconds. If it can be tested here, **don't** test it in a
   browser.
2. **The catalog floor** (`test/games.test.mjs`) — applies to every game whatever
   the technology: opens over `file://`, draws, has a title, fetches nothing from
   outside, fills the screen, offers the exit to the catalog and **switches
   language**. It is the test that enforces the rules in section 1.
3. **The game itself** (`games/<slug>/test/`) — playability and whatever only
   breaks in a browser: touch, drag, a save that persists, a screen that adapts.

### How to write one

`slopkit/testing` provides the scaffold — puppeteer-core with the system's Chrome
(`CHROME=/path` points at another):

```js
import { launchBrowser, open, DEVICES, scenario, check, run } from 'slopkit/testing';

const browser = await launchBrowser();

scenario('planting by dragging works on touch', async () => {
  const g = await open(browser, FILE, DEVICES.phone);
  await g.exec((game) => game.goToBattle(1));
  await g.tap(...g.at(240, 50));                     // the GAME's coordinate
  await g.drag(g.at(300, 400), g.at(520, 500));
  check(await g.exec((game) => game.current().st.planted.length) === 1);
  await g.setLang('pt');                             // and in Portuguese too
  g.expectNoErrors();
  await g.close();
});

await run('my game');
```

### Never sleep a fixed time

`await wait(300)` passes on your machine and fails on the runner, where Chrome
renders in software. Worse: it passes on its own and fails in the middle of the
suite, when nothing before it was buying the missing time. Two tools so you don't
have to guess:

```js
await g.waitFrames(3);                        // let the screen draw
await g.waitUntil((game) => game.ready());    // wait for what actually matters
```

`waitFrames` needs `frames()` on the game's bridge — a counter incremented while
drawing. It is worth exposing: **a screen's list of clickable buttons only exists
after it draws**, so switching screen and clicking in the same instant hits a
screen with no buttons at all. That is how a test here started failing only
inside the suite.

**Changing state is not the same as being drawn.** This is the mistake that has
shown up twice here, the second time only on CI:

```js
await g.waitUntil((game) => game.current().confirming());  // the dialog opened…
await g.waitFrames(2);                                     // …but has no buttons yet
await g.tap(...);
```

Opening a dialog flips a flag immediately; its buttons only enter the clickable
list on the next draw. Whenever the next step is clicking something that just
appeared, put a `waitFrames` between the two.

**`g.at(x, y)` is not a convenience, it is the part that goes wrong most.**
Converting a logical coordinate to a screen coordinate by eye
(`x / 1280 * width`) failed twice during development — once because the canvas
was centred with bars, once because the logical width became elastic. Both times
the test reported a game bug that was a test bug. `at()` reads the measurement
from the game itself, through `window.__game.viewport`. For content inside a
frame, use `atFrame()`, which discounts the scale too.

**Don't look for a button by pixel.** With the text changing language, a bar that
sizes itself to its content moves. Animals exposes `buttons()` on the map screen
and the test finds the button by the action it performs — resistant to
translation and to layout changes.

**Don't assume which language a test starts in.** English is the default, but a
browser asking for Portuguese gets Portuguese — and the machine running the suite
may well be one. Read the current language off the bridge and switch to the
*other* one; that is the contract either way.

Run it before publishing.

## 7. Publishing

A push to `main` runs the tests and, **if they pass**, publishes to GitHub Pages:

- Index: `https://victorlcampos.github.io/slop-games/`
- Game: `https://victorlcampos.github.io/slop-games/<slug>/`

A pull request runs the same tests and does not publish. There is no manual
deploy and `dist/` is not committed.

### The gate

The workflow has two jobs: `testar` builds and tests, `publicar` only publishes.
**The artifact that goes live is exactly the one that passed the tests** — the
publishing job rebuilds nothing. Without that there would be a chance of shipping
a build different from the one that was verified.

What blocks the deploy:

1. `npm run build` — which already fails on its own if any game produces HTML
   with an external reference (rule nº 2) or a `game.json` missing a language.
2. `npm test` — the kit's unit tests + the floor for every game, including the
   flag switch in each one.
3. The Animals vs Monsters test.

What does **not** block it: World Drive's smoke test, which drives on a real
OpenStreetMap map. It is a good test and a terrible gate — it depends on a
third-party public API that goes down and rate-limits. It runs with
`continue-on-error` to give visibility without being able to hold the whole
catalog hostage.

When something breaks, the tests' screenshots go up as an artifact
(`telas-da-falha`): on a layout failure, the image says in one second what the
log doesn't say in twenty.

### Running the way CI runs

Two things change when `CI` is set, both for concrete reasons:

```bash
CI=1 npm test        # reproduces the runner's environment on your machine
```

- **`--no-sandbox`** — the runner runs as root in a container and Chrome refuses
  to start with the sandbox.
- **Software WebGL** (`--use-angle=swiftshader`). The reflex here would be
  `--disable-gpu`, and it **breaks the 3D games**: with no WebGL context, SkiFree
  and World Drive create no canvas at all and the test reports "no canvas" as if
  the game were broken. SwiftShader renders on the CPU — slower, but real.

Chrome comes from the runner (`puppeteer-core` doesn't download a browser, and
that is what keeps the repository light). slopkit's `findChrome()` finds it on
macOS, Linux and Windows; `CHROME=/path` forces another.

Because SwiftShader is slow, a test that sleeps a fixed time passes on your
laptop and fails on the runner. Use `waitFrames()` and `waitUntil()` — see
section 6.

## 8. Code conventions

- **Everything in English: code, comments, documentation, README, commit
  messages.** English is the product's default language, and the repository
  follows the product.

  The exceptions are **proper nouns**: `saci`, `curupira`, `boitata`,
  `bichopapao` stay as they are in Animals vs Monsters' ids. Translating a Saci
  is inventing a creature that doesn't exist — what gets translated is the legend
  that describes him, not his name. The same goes for the games' **slugs**, which
  are published URLs.

- **The text a player reads exists in both languages, side by side.** Never in
  tables separated by language — see section 2c and the reason why.

- **A comment explains why, not what.** The good comments in this repo record the
  trap ("the substitution MUST be a function: the bundle contains `$&`"), not the
  operation.
- **No new dependency without a real need.** Every `npm i` has to justify its
  weight in the final file. When in doubt, write the 40 lines.
- **`src/` in small, thematic modules** — `render`, `input`, `audio`, `world`,
  `entities`. No 3000-line file.
- **A README per game** with the controls and what the game has that is
  interesting.
